Part 01

Introduction

What Angular is, who built it, and why it was rewritten from scratch.

01 · Introduction

What is Angular?

A TypeScript-based, component-driven framework for building single-page applications — maintained by Google, not a third-party project.

It's a framework, not a library

  • Ships with routing, forms, HTTP client, dependency injection, and a CLI — all official, all first-party
  • Opinionated: there's a "correct" Angular way to structure most things
  • Contrast with React, which is a rendering library — routing, state, HTTP are all third-party choices

The basics

  • Created by: Google (Angular team)
  • Language: TypeScript, compiled ahead-of-time
  • Unit of UI: the component
  • Current model: standalone components + signals (no NgModules required since v14–17)
01 · Introduction

AngularJS → Angular

2010 — AngularJS

  • Built by Miško Hevery at Google, open-sourced as a side project turned Google-backed framework
  • Pioneered two-way data binding and dependency injection for the browser
  • Plain JavaScript, no compiler — the whole app ran interpreted

2016 — Angular (v2+)

  • A complete rewrite, not an upgrade — different framework, same team
  • TypeScript from the ground up, component-based instead of controller/scope-based
  • Not backward compatible — hence "Angular" (no JS) vs "AngularJS" as distinct names

Why rewrite instead of iterate?

AngularJS's two-way binding relied on dirty checking — on every change, it walked the entire watched-expression tree comparing old vs. new values. That scaled badly as apps grew, had no real mobile story, and had no compile-time type safety. Angular 2+ replaced dirty checking with a unidirectional change-detection tree, added a compiler (later Ivy), and made TypeScript mandatory — trading a gentler on-ramp for a framework that holds up at scale.

01 · Introduction

What problems does it solve?

State ↔ UI sync

Keeping the DOM in sync with app data by hand doesn't scale past a few pages. Angular's binding + (now) Signals handle that automatically.

SPA navigation

The built-in Router swaps views without full page reloads, with guards, lazy loading and nested layouts out of the box.

Team-scale consistency

Enforced structure, DI, and strict TypeScript mean a 50-person team's code stays legible — less "everyone picked their own tools."

In our own project

CineTrack needed a dozen pages sharing auth state, a persistent sidebar, and live server data everywhere — exactly the case Angular's router, DI-based services, and Signals are built for.

Core Concepts

Structure, components, routing, state, services, HTTP, and rendering — shown with real code from CineTrack.

02 · Core Concepts

Project structure

The standalone model

Since Angular 14–17, components declare their own dependencies directly — no NgModule wiring anything together behind the scenes.

  • Every component lists exactly what it imports
  • No more "why won't this render" NgModule debugging
  • A single component can be bootstrapped directly (see main.ts)

CineTrack's convention

client/src/app/
├── core/        # guards, interceptors,
│              # models, singleton services
├── shared/      # reusable components + pipes
│              # (movie-card, icon, layout...)
└── features/    # one folder per route
               # (dashboard, watchlist, journal...)
02 · Core Concepts

Components

@Component({
  selector: 'app-movie-card',
  standalone: true,
  imports: [RouterLink, IconComponent],
  template: `
    <a [routerLink]="detailRoute()">
      <img [src]="tmdb.posterUrl(media().poster_path)" />
      @if (showWatchedBadge()) {
        <span class="check-dot">✓</span>
      }
    </a>
  `,
})
export class MovieCardComponent {
  media = input.required<TmdbMedia>();
  showWatchedBadge = input(false);
}

A real, reused component

  • input() replaces the old @Input() decorator — signal-based, with .required() enforced at compile time
  • @if / @for / @switch (Angular 17+) replace *ngIf / *ngFor — built into the compiler, not directives
  • This exact tile is reused across 8 different pages in CineTrack — poster grids, watchlist, favorites, similar-titles rails
02 · Core Concepts

Routing

export const routes: Routes = [
  {
    path: 'movie/:id',
    loadComponent: () =>
      import('./movie-details.component')
        .then(m => m.MovieDetailsComponent),
  },
  {
    path: '',
    canActivate: [authGuard],
    loadComponent: () => import('./layout...'),
    children: [ /* every protected page */ ],
  },
];

What's happening here

  • Lazy loading — loadComponent() only downloads a page's code when the user actually navigates to it
  • Guards — canActivate runs before a route loads; ours redirects to /login if not authenticated
  • Nested routes — a layout route with children keeps the sidebar mounted while pages swap inside it
  • Route params — :id binds straight to a component input(), no manual subscription
02 · Core Concepts

State management — Signals

export class AuthService {
  private currentUser = signal<User|null>(null);

  readonly user = this.currentUser.asReadonly();
  readonly isAuthenticated = computed(
    () => !!this.currentUser()
  );

  login(payload) {
    return this.http.post('/auth/login', payload)
      .pipe(tap(res =>
        this.currentUser.set(res.data.user)
      ));
  }
}

Angular's newest reactivity model

  • signal(x) — a reactive box; read by calling it, write with .set()/.update()
  • computed() — derived state, recalculated only when a dependency actually changes
  • Templates that read a signal re-render automatically — no manual subscriptions, no Zone.js-driven "check everything" pass
  • Introduced in v16, now the recommended default over RxJS BehaviorSubjects for component state
02 · Core Concepts

Services & Dependency Injection

@Injectable({ providedIn: 'root' })
export class ApiService {
  private readonly baseUrl = environment.apiUrl;

  constructor(private http: HttpClient) {}

  get<T>(path: string) {
    return this.http.get<T>(`${this.baseUrl}${path}`);
  }
}

// anywhere in the app:
constructor(private api: ApiService) {}

Inversion of control, built in

  • providedIn: 'root' registers a service as an app-wide singleton — one instance, shared everywhere it's injected
  • Components declare what they need in the constructor; Angular supplies it — nothing manually instantiates a service with new
  • Makes testing straightforward: swap a real service for a mock at the injector level, nothing else changes
  • CineTrack has 10+ services this way — auth, TMDb, watchlist, favorites, toast...
02 · Core Concepts

HTTP, interceptors & APIs

export const authInterceptor: HttpInterceptorFn =
  (req, next) => {
    const token = inject(AuthService).getToken();
    if (token) {
      req = req.clone({
        setHeaders: { Authorization: `Bearer ${token}` },
      });
    }
    return next(req).pipe(
      catchError(err => {
        if (err.status === 401) router.navigate(['/login']);
        throw err;
      })
    );
  };

Angular's answer to "middleware"

  • Interceptors sit in front of every outgoing HTTP call — the closest Angular concept to Express-style middleware, but for requests, not routes
  • Ours attaches the JWT to every request and force-logs-out on a 401, once, instead of repeating that in every service
  • Every API call returns an RxJS Observable — lazy, cancellable, and composable with operators like tap, catchError, map
02 · Core Concepts

Rendering methods

CSR (default)

Client-side rendering — the browser downloads JS, then builds the page. What CineTrack uses. Fast after first load, blank until JS runs.

SSR / hydration

Angular Universal renders the first page on the server, then "hydrates" it in the browser — better SEO & perceived load time.

Change detection engine

Historically Zone.js patches async APIs to know when to re-check the UI. Signals (and newer zoneless mode) opt out of that entirely.

Ivy — the compiler underneath

Since Angular 9, templates compile ahead-of-time to efficient instructions rather than being interpreted at runtime — smaller bundles, better tree-shaking, and the foundation standalone components and Signals are built on.

Part 03

Features & Trade-offs

The honest version — what Angular is genuinely good at, and where it costs you.

03 · Features

Advantages vs. disadvantages

✓ Advantages

  • Batteries included — router, forms, HTTP, DI, testing, all official and consistent
  • TypeScript-native — not bolted on, the framework itself is written in it
  • Enforced structure — large teams stay consistent without a style-guide debate
  • Migration tooling — ng update automates most breaking-change upgrades
  • Signals closed most of the reactivity/performance gap with newer frameworks

✗ Disadvantages

  • Steeper learning curve — DI, RxJS, decorators, templates all at once
  • More verbose for small/simple apps than React or Vue
  • RxJS itself is a second learning curve on top of the framework
  • Smaller hiring pool / mindshare than React, though large in enterprise
  • Historically heavier bundles — much improved, but still a fair critique
03 · Features

Performance

What's improved it

  • Ivy compiler (v9+) — smaller, more tree-shakeable output
  • Standalone components — no forced NgModule graph to parse
  • Signals — fine-grained updates instead of a full change-detection sweep
  • Lazy-loaded routes — CineTrack ships ~15 separate page chunks, only the visited one downloads

The honest caveat

On raw DOM-update microbenchmarks, Angular has historically trailed React and especially fine-grained frameworks like Solid or Svelte.

In practice, for a data-heavy real app like CineTrack, the gap rarely matters — network latency to the API and TMDb dominates over framework render time.

03 · Features

TypeScript, developer experience & learning curve

TypeScript support

  • First-class, not optional in practice
  • Strict template type-checking catches real bugs at compile time
  • CLI scaffolds .ts by default

Developer experience

  • Angular CLI — generate, build, serve, test
  • Angular DevTools browser extension
  • Opinionated conventions cut down bikeshedding

Learning curve

  • Steep at first: TS + RxJS + DI + templates
  • Pays off in large, long-lived codebases
  • Gentler now than pre-Signals Angular

04 · Ecosystem

Libraries & deployment

Common libraries

  • Angular Material — official Material Design component library
  • RxJS — bundled, core to the framework's async model
  • NgRx — Redux-style state management (less needed since Signals)
  • Angular Universal — official SSR
  • Nx — the de-facto monorepo/build tool in Angular shops

Deployment options

  • Static CSR build → Vercel, Netlify, Firebase Hosting, GitHub Pages, S3+CloudFront
  • SSR build → any Node host (Render, Railway, a VPS)
  • Docker for containerized enterprise deploys
  • CineTrack: client → static hosting; Fastify API → a Node host; MongoDB Atlas already in the cloud

05 · Comparison

When would you actually choose each?

Choose Angular

Large teams, long-lived enterprise apps, org-wide TypeScript enforcement, and you'd rather the framework decide the conventions for you.

Choose React

Maximum flexibility, the biggest hiring pool, fast-moving startups, or you want React Native code-sharing with mobile.

Choose Vue

Smaller-to-mid projects, a gentler ramp for the team, or incrementally modernizing an existing non-SPA site.

Part 06

Lessons & Challenges

What actually happened building this, not the highlight reel.

06 · Retro

Lessons learned

What paid off

  • Signals made component state noticeably simpler than we braced for — barely any manual subscription management
  • Standalone components cut most of the NgModule boilerplate we expected to fight
  • Strict TypeScript + template type-checking caught real bugs before they ever hit the browser

What we'd do differently

  • We started without git properly set up — lost real work when a teammate's update overwrote local changes
  • Setting up branches and a shared workflow properly, even mid-project, paid for itself immediately
  • An agreed API response shape up front would've prevented several silent bugs (see next slide)
06 · Retro

Challenges we actually hit

Frontend/backend contract drift

Working in parallel without a written API contract meant the client sometimes expected { snapshot } and the server sent { statistics } — a whole page silently showed "no data" instead of erroring loudly.

External API quirks

TMDb has been dropping episode_run_time for newer shows — a naive "hours watched" calculation would've silently shown 0 hours for a fully-watched 26-episode series. Needed a sane fallback.

Merging without shared history

Reconnecting two people's untracked local work meant resolving real conflicts across ~20 files by hand once git finally entered the picture.

Layout at real screen sizes

A stat bar meant to overlap the hero image's edge instead overlapped the call-to-action buttons — only visible once someone actually looked at it on a real screen, not just in the editor.
